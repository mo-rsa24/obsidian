## Quick context: where you are

**What the idea is**

An agent that turns what a `/drip-execute-plan` walk teaches into notes in one shared Obsidian vault, and shows those notes back before the next step that needs them.

**Where the walk is**

Layers 1 to 4 are decided, with all their children. Layer 5 is expanded into five blocks. The `aliases` field and 5.1 to 5.3 are decided. The walk is on 5.4, what sits inside a thing's folder, round 1. One offer waits for a yes: the safety rule while the repository is still public. One check waits on the learner: opening the Obsidian test note.

**What compile would produce today**

Destination A, with four layers decided and two open. It would say what a turn writes, what every note looks like, which pieces do the work and where it runs, and leave the trees and the build order undecided. The load-bearing layer, 5, is still open, so a compile today could not say where any note is filed or how an existing one is found.

## The idea, as it stands

Navigation: ⬅️ [Quick context](#quick-context-where-you-are) | 📋 [TOC](#table-of-contents) | [Next](#the-constraints-pinned-from-disk) ➡️

A writer sits beside every `/drip-execute-plan` walk. When a turn teaches something, the writer files it at three levels: what was done on this project with the real command and the real output, the general rule that holds on any project, and a definition behind each word that carries a concept. The three levels are linked both ways and live in three linked trees (the tool, the practice that uses it, the project where it happened) beside the existing journey mirror. Before a step, the walk looks the vault up and shows the existing note and where it was last applied. A second way in, a pulse, runs the same writer over a plan file nobody is walking.

The purpose is independence. `[yours]` "I want to build all these different skills where I can do things independently so having them accessible with images shown where navigation is easy would be great." So a note is finished when the technique can be done from the note alone, with no plan and no assistant open. Its pictures are shown in the note, and getting to it and around it is easy. Layer 2 owns how.

What the vault is for, in the learner's words. `[yours]` "in our interactions, you provide so much information that is helpful. But it becomes noise in the background that gets quickly forgotten because I run lsof -i :8000 once, or different times in isolation making the learning process inefficient. The idea is to convert your output and responses into useful information that I can always go back to." And: "every walk where we document something means that we have a strong reference of where we could learn further and deeper ... we can just practice and refer back ... It prevents loss." So the test of the whole design is that something explained once in a walk can be found, re-read and practised later without the walk.

A general note teaches its technique inside a sandbox, never in isolation. `[yours]` "you need to be able to provide instructions to get to a point where I can do that and everything surrounding it. Because things only become easier to understand and transformed into working knowledge once we understand the application and context ... Almost like a sandbox for the concept being taught. If we are learning about `lsof -i :8000` we first need something to run, and something to check." So the note carries what has to be installed and how to check it, the setup that makes something exist to act on (seed data for a join, a server on a port for `lsof`, an image for `docker run`), what that looks like before, the technique, the output, why it is needed, and more than one worked example. The agent builds that sandbox itself from an empty folder, so the output shown is the output of the instructions written. Layers 2 and 4 own how.

Every note has to pass three tests. Documented: a person who knows the field accepts it as a record, with the exact command, the real output and the reason. Reusable: it applies on another project without opening the one it came from. Findable: it is listed in its parent's map, its name can be guessed, and it opens with a map of itself.

The field's names for the parts: a note that maps its children is a structure note, or a map of content. A folder holding a note of its own name is a folder note. The four kinds of documentation in Diátaxis (tutorial, how-to, reference, explanation) line up with the levels: the project note is the how-to as it was done, the general note is reference plus explanation.

## The layers

Navigation: ⬅️ [The constraints](#the-constraints-pinned-from-disk) | 📋 [TOC](#table-of-contents) | [Next](#the-decisions-the-brief-asks-for-and-the-layer-that-owns-each) ➡️

### 1. ✅ What happens when a turn of a walk ends

Mark: decided.

**Decided: what the pulse writes at the project level.** A project note only for a step whose plan line is ticked with evidence, or whose walk map records what was seen. A step with no evidence gets no project note. The reason: a project note built from the plan's reference output would put the plan's answers (plan 54: `rows=569033`) into the vault before the learner has found them, and 2 of 1,094 task lines in the prototype journey carry evidence today.

**Decided: two lists in every general note.** "Taught in" links the learning-tree plan steps that teach the technique, with no output and no numbers. "Applied in" links the project notes where it was done. A step moves from the first list to the second when it is walked. The reason: an unwalked plan stays reachable from the general note without a project note that would carry its answers.

**Decided: how far explanation goes without a walk behind it.** Explanation is written inside a note a walk already made, and for the concepts that note names, one step out, under the 1.1 rule. Whole subject areas with no walk behind them are not written. The reason: the vault stays a record of what was met and applied, so "Applied in" is never empty by design, and a subject no walk reaches is a journey's job through `/submerge`.

- [x] 1.1 Which lines earn a rule note, and which words earn a term note (brief decision 1)
  - Decided. A line earns a place in a general note when it survives having the project's nouns removed: `uv add --group eda pyarrow duckdb` leaves `uv add --group <group> <packages>`, and `rows=569033, columns=221` leaves nothing. The general note belongs to the named thing (`uv`) and the line becomes a section inside it.
  - Decided. A word earns its own definition only when the source marks it (a heading, a bolded lead-in, a glossary entry) or the learner asked about it or was corrected on it, and it has a named neighbour to differ from. On the brief's streaming sentence this gives 2 entries, stream and batch. The reason: both signals are checkable on disk, and one sentence costs 2 entries where "every carrying word" costs 6.
  - A question or a correction always earns a write. A repeat of something already noted writes only its "Applied in" entry.
- [x] 1.2 How a general rule is told from a project fact, and a tool from a practice (brief decision 2)
  - Decided. Three tests, in order. First, remove the project's nouns: if nothing is left, it is a project matter. Second, look for syntax that one tool parses (a command, a flag, a function, a keyword): a line that has some is a tool line, and a line with none is a practice. Third, on the project side, ask whether a technique is in it: an applied technique is a vault project note, a bare fact about the system or its data is not.
  - The second test was first worded "swap the tool for a rival and see whether the sentence stays true". `docker run -p 8000:8000 <image>` broke it: `podman run` accepts the same flags, so the swap leaves the sentence true and calls a command a practice. The syntax wording gives the right answer on every line tried: `uv add --group`, `docker run -p`, `lsof -i :8000`, `silo_x.merge(..., indicator=True)` at `x.py:866`, `amp.groupby("Sku").size()` at `x.py:376` and `pd.crosstab(...)` at `x.py:584` are tool lines, and "stream and write bounded batches", "check what holds the port before starting a server" and "check which keys match before trusting a join" are practices.
  - The second test has three outcomes. `[yours]` "for the more general things it will be like Deep learning/Convolutional neural networks for example." A convolutional neural network has no syntax that one tool parses, and it is not a way of working either, so the two-way test mislabels it. A general thing is therefore one of three kinds: a tool line (it has one tool's syntax), a practice (an instruction with no syntax: "check which keys match before trusting a join"), or a concept (a named thing with a definition and a mechanism: a convolutional neural network, a PID, TCP). A large concept takes the full two-file shape. A small one is the concept entry described under 2.1.2.
  - A practice note is made on first sight only when the source marks the line as a decision or a rule, the same signal as 1.1. Otherwise the rule sits in the tool note's "when to reach for it" section until a second tool needs it.
  - Decided. A bare project fact ("`BARCODE` has leading zeros in SAP") goes to the journey's own `context/`, `environment/` or `report/` through the walk's existing `note` control, and the vault does not hold a list of facts. The reason: a session doing the work reads the journey's folders and never the vault, `note` already exists, and a fact about one system is not a skill carried to another project.
  - Decided. The reason line. When a bare fact is the reason a technique was chosen, the vault project note quotes it once, dated, as that technique's "Why" ("read `BARCODE` as text, because SAP barcodes carry leading zeros"). A fact that explains no choice stays out. The reason: without the fact the project note records what was done and loses why, and the Documented test asks for the reason. Its cost: the sentence exists in two trees, so it is written as a record of what was true on that date and is never kept in sync.
- [x] 1.3 The check that filed code does what the sentence beside it says
  - Three checks before a line is filed. Claim to line: every checkable claim in the sentence points at a line of the code filed with it. Byte for byte: the command is copied from the turn's record into a code fence and scanned for characters a shell rejects (an en dash, curly quotes, a non-breaking space), which is the check `conda update –all` in `Conda.odt` never got. Output attached: each command block carries the output of a real run and a mark saying whose run, on which machine, on what date.
  - On `stream_sap` at `x.py:631-642` against the brief's sentence, 1 of 3 claims finds a line. "One row at a time" is `for n, row in enumerate(ws.iter_rows(...))`. "A fixed batch of 1,000 in memory" has no line: `keep` grows with every kept row, and `n % 100_000` only prints progress. "Writing each batch out" has no line: the function returns one DataFrame.
  - When the check fails, what ran wins. The vault note describes what the code that ran does, and the mismatch with the plan's or chapter's sentence goes back to the walk as a candidate for its `fix` control. The writer never edits a plan or a chapter.
  - In a general note, each claim is proven by an output of the sandbox. The pair "without it, then with it" is the strongest form: the list version's memory grows with the row count and the batched version's does not.
  - Decided. A command step the learner closed on words alone is filed at once with the command and those words, its block is marked as missing its output, and the note stays unfinished until the output is attached. The reason: calling it finished repeats `Conda.odt`, nine commands with no output, and asking for the output first stops the walk on every turn.
  - The three checks on the `uv add` turn, from run 1: the command scans clean (`conda update –all` scans as U+2013 at position 13), the output is 11 lines ending `+ duckdb==1.5.6` and `+ pyarrow==25.0.1`, and its mark reads "ran 2026-10-01, PC (WSL), uv 0.8.13, by the writer in an empty folder".
  - Decided. What counts as a step's output is read off the step. A click-path step is complete on the learner's words. A step whose plan limits what may be copied (plan 54: timings and counts, no product values) is complete on those counts. Any other command step needs its text output or a screenshot. The reason: the walk already ticks a click-path step on the learner's words, and the vault should not hold a stricter bar than the plan.
  - Decided. The writer picks up a screenshot taken during the turn: the newest file in `C:\Users\molef\Pictures\Screenshots` whose time falls inside the turn is copied beside the note under the name of the heading it proves and embedded, and the walk shows the pickup for one word of confirmation. The reason: filing a screenshot cost one keystroke in the old system and should cost no more now. The Mac's screenshot folder is layer 4's to name.

You run a step and say what you saw. Before the next step appears, a writer takes the record of that turn (the command, your output, what you asked, what you corrected) and asks whether the turn taught anything. If not, it writes nothing. If so, it looks up whether the vault already has a place for the thing. It writes what you did, with your real output, into the note for this project. It writes what holds on any project into the general note, running the command itself in a throwaway folder so the example output is not your project's. It links the two both ways, checks every link it touched, and adds any new note to its parent's map. The next walk that reaches a step using the same thing looks the note up first and shows it, with where you last applied it. The second way in runs the same writer over a plan file nobody is walking.

The parts that paragraph names, each owed an account in a later layer: the record of a turn, the test for "taught something", the lookup, the project note, the general note, the throwaway folder, the link check, the parent's map, the read-back before a step, the pulse.

The open decision: a plan nobody has walked has commands and reference output, and it has no run of yours, no question and no correction. The pulse can write the general note in full. What it writes at the project level is undecided. The options and the fact that picks between them are under [Open decisions](#open-decisions).

### 2. ✅ What a note looks like, and what the walk shows before a step

Mark: decided.

- [x] 2.1 The general note's parts, and how they are split
  - Twelve parts, drawn on pandas `merge`: the map of itself, what it is in one line, the form and its picture, when to reach for it, without it and then with it, try it yourself (the sandbox), other ways, the derivation, tips, the cheatsheet and docs links, "Taught in", "Applied in".
  - Decided. Two files per thing: a reference note for looking it up and a lesson note for learning it. The reason: the two readers want different things, and Diátaxis keeps reference and tutorial apart for that reason.
  - Decided. Three conditions let two files stay one thing. First, the thing is a folder, the reference note is the note named after that folder, and the lesson and the pictures sit inside it, so every link from outside lands on the reference and the thing keeps one address. Second, the reference shows one worked example per form by embedding that section of the lesson (`![[lesson#heading]]`), so the command and its output are written in one file and shown in two. Third, the writer sorts new material by one question: anything that came from a sandbox run goes to the lesson, anything else goes to the reference.
  - The split. Reference: the map, what it is, the form and its picture, when to reach for it, other ways, tips, the cheatsheet and docs links, "Taught in", "Applied in". Lesson: without it and then with it, try it yourself, the derivation.
  - [x] 2.1.1 The parts of "try it yourself", and where a sandbox's files live
    - Nine parts in a fixed order, built for real on `lsof -i :8000` in run 2: what you need, the command that checks for it, what to do when it is missing, the setup that makes something exist, a look at it before, the failure without the technique, the technique, another way, the clean-up.
    - Decided. The seed and the setup are written inline in the lesson as code blocks while they fit on one screen, and move to files in a `sandbox/` folder beside the lesson above that. The reason: typing two commands is part of the lesson and nothing beside the note can go stale, and a seed longer than a screen is not worth retyping.
    - Every output the lesson shows is read. `[yours]` "in your sandbox lesson, I should be able to interpret and read command, PID, user, FD, type, device, size/off, node, name have them explained and visualized with prompt-storyboard and render-diagrams." So after each output comes a reading: one row per field, with the field's name, its value in this run and how to read it. A field is explained in full the first time it appears in a thing, and later examples say only what differs.
  - [x] 2.1.2 How many pictures a thing gets, and of which kinds
    - Four kinds. The form picture is drawn: the syntax skeleton with each slot named. The output picture is rendered from the captured text of a real run by a script, with a numbered marker over each field, and is never drawn. The mechanism picture is drawn: what the output's fields point at in the system, as a named cast with arrows. The learner's own screenshot belongs to the project note.
    - On `lsof -i :8000`, from run 3: the mechanism is one process (`python3`, PID 228372, user molef) holding four descriptors, 0 reading `/dev/null`, 1 and 2 writing a log file, and 3 open both ways on socket 7636456, which is TCP, listening on `*:8000`. `/proc/228372/fd/3` shows `socket:[7636456]`, the same number as the DEVICE column.
    - The drawn pictures go through `prompt-storyboard` for the prompt and `render-diagrams` for the render. The mechanism picture's faithfulness note lists the labels that must appear, so the render is checked against the real run's values.
    - Decided. A thing gets two drawn pictures, the form and the mechanism, each from one prompt, and a rendered output picture on every worked example. A storyboard set is made on demand for a thing whose mechanism has steps. The reason: a drawn picture is a Codex render checked twice with up to three revision rounds, and an output picture is made by a script from text already captured.
    - Decided, by the art-direction questions on 2026-10-01: the look is Empty for every drawn picture in a general note, the mechanism ladder stops at level 0, and the mechanism picture is a subject picture. The first prompt written this way is [the `lsof` mechanism prompt](diagram-prompts.md#prompt-1-subject-one-process-holds-port-8000), rendered as [the `lsof` mechanism picture](diagrams/lsof-01-one-process-holds-the-port.png).
    - What rendering the output picture showed, from runs 4 and 5: the route through `rich` to SVG and `cairosvg` to PNG lost the monospaced font, so the columns and the markers drifted apart, and its default theme is dark. Drawing the captured text with Pillow in DejaVu Sans Mono on a light background gives [a correct picture](runs/lsof-output.png): nine markers, each centred over its header word, the row beneath. So the script names its own font, and a rendered output picture is checked by eye like any other picture.
    - The output picture and the mechanism prompt use one run's values (PID 232663, socket 7743610), so the two pictures of one lesson agree.
    - `[yours]` on the mechanism prompt: "what about illustrative diagrams that don't only visualize lsof but also what each of the columns mean in the context of computing? like what is a PID, what is TCP, Type? The illustrations serve to explain a concept further to make it interpretable not only show something. It is meant to cement my understanding and highlight the significance of something." The prompt as first written showed one instance and explained nothing. It now carries six callout chips, one per part, each saying what the part is for.
    - `[yours]` "you can see why multiple diagrams are helpful because you can see the components and their significance and how they work together for lsof on top of `runs/lsof-output.png`." So a lesson's pictures are read as a set: the output picture shows what the terminal printed, the mechanism picture shows how the parts work together, and the concept pictures say what each part is and why it matters.
    - Decided. A concept picture is drawn once per concept and lives with the concept. The reason: a concept such as PID is named by several things (`lsof`, `ps`, `kill`, `top`), and a picture redrawn in each lesson drifts. A word that earns a definition under 1.1 also earns one drawn picture of what it is and why it matters, kept in that concept's own entry and embedded wherever a lesson's field table names it. For `lsof` that is about five concepts: process and PID, file descriptor, file type, socket, and TCP with its port. The columns that only mean something inside `lsof` (DEVICE, SIZE/OFF, NODE) stay in its own table. A thing keeps its two drawn pictures.
    - Decided. A thing gets a third drawn picture, the deep-dive sheet: one page that composes the others. `[yours]` "settle. You could add a third one." The model is [the sheet the learner supplied for `lsof -i :8000`](diagrams/refs/lsof-deep-dive-sheet-example.png): the command taken apart, the example row with its markers, one card per field (what it means to the operating system, a small picture, the value in this run), how the pieces work together as a chain, and where the tool gets its information. In the style guide's words this is the set's capstone. The reason: the form and the mechanism each answer one question, and the sheet is the single page to return to.
    - What the supplied sheet shows about checking one. Its marker over PID reads 3, so the row counts 1, 3, 3, 4. Its NAME card draws `eth0`, `wlan0` and `lo`, and this machine has `lo`, `eth0`, `docker0` and a bridge, with no `wlan0`. A sheet carries about 60 pieces of text, so its faithfulness note lists every one, and example values come from the run or are labelled as examples.
    - What the sheet needs from the style guide. It holds nine cards, a ten-step chain and five titled sections, which is over the guide's limit of seven primary components and its rule against paragraphs inside an image. The sheet is therefore a named exception, to be written into the guide at the merge.
    - Text inside a picture cannot be searched in Obsidian and cannot carry a link. So everything on the sheet also exists as text in the lesson: the field table, with each field's name linking to its concept.
  - [x] 2.1.3 What the derivation part holds when a thing has no mathematics
    - Decided. Three cases. Where a number follows from other numbers (a merge's row count, the streamed memory bound), the part holds the full derivation and then the worked numbers. Where there is a mechanism and no such number, it holds the mechanism walked in numbered steps along the mechanism picture, each step with the line of output that shows it. Where there is neither, it holds one line saying nothing is derived and why. The part is never left out, because a missing part cannot be told from a forgotten one.
- [x] 2.2 The project note and the map note
  - The project note holds one heading per technique applied. Under each heading: the sentence from the plan or chapter, the command as it was run, the learner's output as text and as a picture, the reason line, and the link up to the general note. The general note's "Applied in" entry links to that heading.
  - The map note is the note named after its folder. Each line names one child and says what it is for.
  - Ground: plan 54 already names its vault note, `54-large-file.md`, in the journey's mirror folder, so the plans on disk expect one note per plan.
  - `[yours]` on the three fixed options: "Rather intelligently see how you can group them. Because there are tradeoffs and we want the most effective. But otherwise looking good."
  - Decided, on "Looking good for documenting the project in Obsidian": group by what was being done on the project, and split when crowded. The reason: it is the one grouping that lands an "Applied in" link on a heading, keeps an address that plan renumbering cannot move, and reads as one piece of work. A project note starts as one note per activity, named in the practice tree's words, and the activity is read off the plans, which already mark it (10 plans carry "Region: T2, the data a senior reads"). Inside it, one heading per thing done, in the order the work runs, each naming the techniques it applied and the plan step it came from. The plan number and the date are fields on the heading and never the note's name. When a note passes about 10 headings, the point where the map at its top stops fitting on one screen, it becomes a folder of the same name whose note maps child notes grouped by sub-activity, and every link into it is rewritten and checked.
  - On region T2 that gives one folder, with four child notes read off the plan titles: reading the specification and the rows (plans 52, 53, 55), making a large file workable (54), finding keys and reconciling records (56, 60), and questions, filters and samples (57, 58, 59, 61).
- [x] 2.3 The states a note can be in, and whether it arrives final or as a draft (brief decision 4)
  - Each part carries its own state. A command block is run (with whose run, which machine, what date), missing its output, or not runnable on the machine that wrote it. A picture is waiting or rendered. A sandbox is built from an empty folder, or not.
  - `[yours]` "you could also have sections/chapters of explaining stuff you know. Does not have to be prompted by code or math? But it is easier with code."
